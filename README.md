# Supply Chain Operations Analytics

A SQL + Python + Tableau project that builds a supply chain dataset from scratch, then uses it to answer one question: **where is this supply chain actually losing money, and which supplier do we fix first?**

**[→ View the interactive dashboards on Tableau Public](https://public.tableau.com/app/profile/nathaniel.harris8003/viz/SupplyChainOperationsAnalyticsproject/SupplyChainReview)**

---

## The headline finding

On-time delivery sits at **84.3%** against a 90% target. The gap is not spread evenly across 30 suppliers — it concentrates.

**Meridian Components** is the #2 supplier by spend ($7.07M across 323 orders) and the single worst cost-control offender in the book:

| | Meridian Components | Next-worst supplier |
|---|---|---|
| Cost variance rate | **6.15%** | 1.40% |
| Share of all cost variance | **82%** ($409.8K of $501.4K) | — |

The variance is not noise, it is a trend: Meridian drifted from **0.63% to 12.73% over eight quarters** while nobody renegotiated. Every other supplier holds near zero. One supplier relationship accounts for four fifths of the overrun on a $56.5M book.

A second finding runs the other way. Cheap freight is not cheap:

| Shipping mode | On-time | Avg cost/order | Avg transit |
|---|---|---|---|
| overnight | 90.4% | $1,607.67 | 1.8 d |
| express | 88.3% | $919.39 | 5.2 d |
| standard | 84.8% | $389.77 | 11.7 d |
| **economy** | **75.8%** | $117.30 | 21.0 d |

Economy is the cheapest line item and the worst service level — a 1-in-4 miss rate. The saving is real but it is being paid for in expedites and stockouts elsewhere.

## Metric definitions

Most of the analytical work in this project was deciding what the numbers mean, not writing the SQL. Two definitions matter enough to state up front, because picking the wrong one reverses the conclusion.

**On-time** = the order arrived on or before `orders.expected_delivery_date` — the date promised to whoever raised the requisition — measured **only over shipments that have actually arrived**.

Two traps avoided here:

1. **Undelivered shipments are excluded from the denominator, not counted as late.** 52 of 3,108 shipments are still in transit. Counting them as misses penalises recent orders and makes the fastest modes look worst, because their shipments are the newest.
2. **Scored against the order promise date, not `shipments.expected_arrival_date`.** The latter is the carrier's own ETA after pickup, and that window is padded differently by mode. Scoring against carrier ETA produces this:

   | | vs order promise | vs carrier ETA |
   |---|---|---|
   | overnight | 90.4% | 46.5% |
   | economy | 75.8% | 77.4% |
   | **overall** | **84.3%** | 61.5% |

   The carrier measure rates economy the *best* mode and overnight the worst — the exact inverse of the truth. It answers "did the carrier hit its own estimate," which is not the question the business is asking.

**Portfolio on-time is shipment-weighted (84.3%)**, not an unweighted mean of per-supplier rates (81.4%). Unweighted lets a supplier with 20 orders move the headline as much as one with 300 — and this dataset contains several tiny suppliers with terrible metrics and negligible spend.

**Spend** is `orders.order_cost` (actual), never the supplier's nominal contract rate. `suppliers.on_time_rate` is deliberately excluded from the Tableau extract: keeping a stored nominal rate alongside a computed actual rate gives the workbook two competing answers to the same question.

## About the data

**The dataset is synthetic and generated by `python/generate_data.py`.** This is stated plainly because it changes how the findings should be read.

It is not random noise. Nine patterns are deliberately planted so the dashboards have real structure to surface rather than uniform static — a degrading supplier, Q4 seasonality, a cheap-but-unreliable shipping mode, Pareto spend concentration, progressive cost drift on one supplier, slow-moving stock, and a tail-supplier trap where tiny suppliers post terrible metrics on negligible spend. They are documented at the top of the generator.

The generator is **seeded (`SEED = 42`) and deterministic**, so every figure in this README, every CSV, and every screenshot regenerates byte-identical. The analysis, the metric definitions, and the modelling decisions are the real work; the rows are a controlled environment to do it in.

## Data model

Five normalized tables in SQLite. Every analysis joins through `orders`.

```
suppliers ──┬──< products ──< inventory
            │        │
            └──< orders >──┘
                   │
                   └──< shipments
```

| Table | Grain | Key columns |
|---|---|---|
| `suppliers` | one row per supplier | `supplier_id` PK, `country`, `lead_time_days`, `quality_score` |
| `products` | one row per SKU | `product_id` PK, `supplier_id` FK, `category`, `reorder_point`, `standard_unit_cost` |
| `inventory` | one row per SKU per warehouse | `inventory_id` PK, `product_id` FK, `quantity_on_hand`, `quantity_reserved` |
| `orders` | one row per purchase order | `order_id` PK, `supplier_id` FK, `product_id` FK, `order_cost`, `expected_delivery_date`, `actual_delivery_date` |
| `shipments` | one row per shipment | `shipment_id` PK, `order_id` FK, `shipping_mode`, `shipping_cost`, `actual_arrival_date` |

### The one modelling decision worth explaining

`python/export_master.py` flattens all five tables into **one order-grain CSV** (3,175 rows × 50 columns) rather than exporting pre-aggregated files per question.

The first version of this project exported eight separate CSVs, each already aggregated to a different grain — one row per supplier, per product, per shipping mode. In Tableau each file becomes its own data source, and a filter only applies within one data source. A supplier filter could not reach the shipping file, because aggregating to shipping mode had already thrown the supplier column away. The dashboards could not be filtered as a set.

Exporting one flat table at the lowest grain and letting Tableau do the aggregating means every KPI on every page is a calculation over the same source, so one filter drives the entire story. The `1:1, no fan-out` check printed by the export script guards the join: 3,175 orders in, 3,175 rows out.

## Reproducing this

No credentials, no external services. Requires Python 3 with `pandas`, `matplotlib` and `seaborn`.

```bash
python3 python/generate_data.py        # build supply_chain.db  (deterministic)
python3 python/export_master.py        # → outputs/supply_chain_master.csv  (Tableau source)
python3 python/export_to_csv.py        # → 8 per-question CSVs
python3 python/create_visualizations.py # → visualizations/*.png
```

`generate_data.py` prints its table counts and `export_master.py` prints the headline KPIs, so a successful run self-verifies against the figures table above.

If the repo sits on a network- or cloud-synced folder, SQLite file locking can fail. Both scripts accept an explicit DB path to work around it: `python3 python/export_master.py /tmp/supply_chain.db`.

## Caveats

Stated because an analysis that hides its own limitations is not finished.

- **One warehouse row per SKU in the Tableau extract.** `inventory` holds 70 rows across 57 products — some SKUs are stocked in multiple warehouses. `export_master.py` attaches the lowest `inventory_id` per product, so the extract sees one warehouse per SKU. This is why the dashboard reports **12** SKUs below reorder point while querying all inventory rows net of reserved stock returns **18**. For a supplier- and cost-focused analysis this is acceptable; a warehouse-level stocking analysis would need a separate inventory-grain extract.
- **67 orders have no shipment record** and 52 shipments have not arrived. Both are excluded from delivery metrics rather than imputed.
- **Cost variance is actual vs the planned cost recorded on the order.** It does not separate price increases from quantity or FX effects, so "Meridian is 6.15% over" is the symptom; the cause needs contract documents this dataset does not contain.
- **The 90% on-time and 21-day cycle-time figures are targets, not benchmarks.** They are reasonable for the scenario but not derived from the data, so the "−5.7 pts" and "+4.0 d" gaps are only as meaningful as the targets.
- **Synthetic data.** See [About the data](#about-the-data). The method transfers; the specific suppliers do not exist.
